# Prometheus & Alertmanager – Metrics and Alerts

This document explains how **Prometheus and Alertmanager** are used in ft_transcendence:

- What Prometheus is and what it scrapes.
- How the `prometheus-pre` helper container generates configs.
- How Alertmanager fits into the picture.

For what metrics and alerts matter for online Pong, see:

- `docs/to0nsa/workflow/MonitoringAndObservability.md`
- `docs/to0nsa/docker/MonitoringStack.md`

---

## 1. What Prometheus is (in this repo)

Prometheus is a **time‑series database and metrics scraper**:

- It periodically scrapes `/metrics` endpoints exposed by services.
- Stores metrics (counters, gauges, histograms) with labels for querying.
- Powers Grafana dashboards and Alertmanager alerts.

In ft_transcendence, Prometheus:

- Scrapes:
  - Node/Fastify services:
    - backend, matchmaking, game‑gateway, game‑server, allocator, scorer, chat.
  - Nginx exporter (Nginx metrics).
  - cAdvisor (Docker/container metrics).
- Uses service labels (`service="matchmaking"`, `service="game-server"`, etc.) added by `@utils/metrics`.

## 2. Config generation via `prometheus-pre`

Instead of maintaining a static `prometheus.yml`, this project uses a **helper container** to generate configs:

**File:** `monitoring/docker-compose-base.yml`

```yaml
prometheus-pre:
  build:
    context: ./monitoring/prometheus-pre/
  environment:
    - ALLOCATOR_PORT=${ALLOCATOR_PORT}
    - BACKEND_PORT=${BACKEND_PORT}
    - GATEWAY_PORT=${GATEWAY_PORT}
    - MATCHMAKING_PORT=${MATCHMAKING_PORT}
    - SCORER_PORT=${SCORER_PORT}
    - CHAT_PORT=${CHAT_PORT}
    - GAME_SERVER_HTTP=${GAME_SERVER_HTTP}
    - GAME_SERVER_PORT=${GAME_SERVER_PORT}
    - MAIL_HOST=${MAIL_HOST}
    - MAIL_FROM_RAW=${MAIL_FROM_RAW}
    - MAIL_USER=${MAIL_USER}
    - MAIL_PASS=${MAIL_PASS}
    - ALERT_MAIL_TO=${ALERT_MAIL_TO:-test@example.com}
    - ALERT_WEBHOOK_URL=${ALERT_WEBHOOK_URL}
  volumes:
    - prometheus-config:/etc/prometheus
    - alertmanager-config:/etc/alertmanager
  restart: no
```

`prometheus-pre`:

- Reads environment variables for:
  - Where to scrape (ports and hostnames of app services).
  - Where to send alerts (email/webhook).
- Writes:
  - `/etc/prometheus/prometheus.yml` – Prometheus scrape targets and alerting rules.
  - `/etc/alertmanager/alertmanager.yml` – Alertmanager receiver config.

Prometheus and Alertmanager containers mount these volumes **read‑only**, so they start with the generated config.

## 3. Prometheus service

**File:** `monitoring/docker-compose-base.yml`

```yaml
prometheus:
  image: prom/prometheus
  restart: unless-stopped
  depends_on:
    prometheus-pre:
      condition: service_completed_successfully
  command:
    - '--config.file=/etc/prometheus/prometheus.yml'
    - '--storage.tsdb.retention.time=30d'
    - '--storage.tsdb.retention.size=1GB'
  volumes:
    - prometheus-config:/etc/prometheus:ro
  networks:
    - prod-private
```

Key details:

- Depends on `prometheus-pre` so config exists before startup.
- Retains metrics:
  - Up to 30 days **or**
  - Up to 1 GB of storage (whichever comes first).
- Runs on the internal `prod-private` network:
  - Scrapes services by Docker DNS name (`backend`, `matchmaking-service`, `game-server`, etc.).

Scrape targets (conceptually):

- `http://backend:<port>/metrics`
- `http://matchmaking-service:<port>/metrics`
- `http://game-gateway:<port>/metrics`
- `http://game-server:<http-port>/metrics`
- `http://allocator:<port>/metrics`
- `http://scorer:<port>/metrics`
- `http://chat-service:<port>/metrics`
- `http://nginx-exporter:<port>/metrics`
- `http://cadvisor:<port>/metrics`

(Exact ports are filled in by `prometheus-pre` using env vars.)

## 4. Alertmanager

Alertmanager handles **notifications** when Prometheus alerts fire.

**File:** `monitoring/docker-compose-base.yml`

```yaml
alertmanager:
  image: prom/alertmanager
  restart: unless-stopped
  depends_on:
    prometheus-pre:
      condition: service_completed_successfully
  volumes:
    - alertmanager-config:/etc/alertmanager:ro
  networks:
    - prod-private
    - prod-public
```

Key details:

- Uses config generated by `prometheus-pre` (via `alertmanager-config` volume).
- Attached to both:
  - `prod-private` – to receive alerts and talk to Prometheus.
  - `prod-public` – so email/webhook notifications can reach the internet (if configured).

Alert rules (conceptual examples, configured in `prometheus-pre`):

- Service down or `/health` failing.
- High error rates on critical endpoints.
- Game server node score too high (overloaded).
- Redis or DB unavailable.

Alertmanager routes these to:

- Email destinations (`ALERT_MAIL_TO`).
- Optional webhooks (`ALERT_WEBHOOK_URL`), e.g. Slack, Discord, or custom handlers.

## 5. How this fits with the rest of the stack

- Node services instrument metrics via `@utils/metrics`, exposing `/metrics`.
- Nginx and containers provide additional metrics via exporters (see `MetricsCollectors.md`).
- Prometheus scrapes all of these and stores time series.
- Alertmanager, configured by `prometheus-pre`, watches for unhealthy conditions and notifies operators.
- Grafana uses Prometheus as a data source to visualize these metrics; see `Grafana.md`.

Together, Prometheus and Alertmanager are the **central metrics brain** of the observability stack.
